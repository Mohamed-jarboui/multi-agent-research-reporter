Multi-Agent Research Reporter

Build report · last update 2026-10-30

Give it a topic: a supervisor plans the report, workers research the sections in parallel, a critic checks sources and gaps, and a writer assembles a cited report. The pipeline now exists up to the writer (R2). The headline result will be a measured comparison against a single agent doing the same job: quality, cost and latency on 12 topics. That comparison does not exist yet (it is stage R3).

R0 · Setup and single-agent baseline merged

What was built

  • A ReAct research agent on LangGraph: it plans 3 to 5 questions about a topic, searches, reads pages, and writes a Markdown report with numbered citations and a sources list.
  • Two read-only tools: web_search (Tavily if a key is set, DuckDuckGo otherwise) and fetch_page (readable text, capped at 8,000 characters per page).
  • A provider layer copied from the eu-ai-act-copilot project (Gemini and Groq, fallback between them, retries, usage records).
  • Hard run budgets (15 steps, 150,000 tokens, 300 s, 0.50 USD) and a trace per run saved to runs/<run_id>.json (git-ignored).
  • Project scaffolding: uv project, CLI (uv run reporter baseline "<topic>"), CI for lint and tests, and the figure script behind this page. 77 tests pass and the linter is clean; the tests use fake models and fake tools, no network.

How it works

  START([start]) --> plan

3-5 questions"] --> think

Each turn the model answers with a JSON action (web_search, fetch_page or finish) and says which planned questions the page answers. The code calls the tool and records the page. check stops the loop when every question has at least 2 pages read, when any budget limit reaches 80%, when the model call fails, or after 3 unparseable replies in a row. A finish before coverage is met is refused twice, then accepted. The writer only sees the pages that were read, and the code appends the sources list itself.

What broke, and what was fixed

The baseline did not work well in these runs. It is the weak baseline the multi-agent system will be compared with, and the numbers above are that baseline on a bad day for the free tier. They should not be read as a flattering or a final measurement.
What brokeEvidenceStatus
Empty model replies from Groq openai/gpt-oss-120b. Steps flagged with an empty-reply note: 7 (failed SLM attempt), 3 (counted SLM run), 4 (carbon capture run). Almost every call went to this model. Partly fixed: an empty reply is retried once at temperature 0.7 (at temperature 0 the same empty reply came back). It reduced but did not remove the problem.
Rate limit: Groq answered HTTP 429 on tokens per minute (limit 8,000) after Gemini quota fell through. All providers failed. The first SLM attempt died with AllProvidersFailedError; no report. Gemini handled only 3 steps of it (the plan and one think step). The counted re-run hit the same 429 at step 11. Not fixed. The run was repeated once. The agent now writes a fallback report from the pages already read when the model fails, which is what produced the SLM report from only 2 sources.
Citations to sources that do not exist. The counted SLM report cites [3] and [4] but has only 2 sources (invalid_citations = [4, 3]). Reading the report, it also contains grouped citations such as [5, 6], which the checker's pattern ([n] only) does not catch, so the true count is probably higher. Detected and recorded in the trace, not corrected. Deterministic citation checks are planned for R2.
The carbon-capture run lost its time on one PDF. One 169 s fetch of a PDF that fetch_page then rejects (it is application/pdf). Nothing readable was collected before budget_seconds; the report is the placeholder text. Not fixed, not re-run. Needs a shorter fetch timeout or an early content-type check; neither is in R0.
Agent tried to re-read a page. 1 tool error in the counted SLM run ("you already read this page"). Handled by design: the agent refuses the repeat and the model chooses another source.

PR #1 (merged).

R1 · Supervisor and parallel workers merged

What was built

  • A supervisor: one model call turns the topic into 3 to 6 self-contained section briefs (title, goal, scope, what to exclude, expected output).
  • Parallel workers: LangGraph Send fans each brief out to a worker that runs a short search-and-read loop with the R0 tools (6 think steps, up to 4 pages) and returns structured findings that cite only pages it actually fetched. A failed worker is retried once, then marked incomplete.
  • A deterministic merge: joins the worker results into one research record with stable global source numbers and a Markdown digest. There is no model-written report yet; the writer is R2.
  • Shared limits: one locked run budget (36 steps, 300,000 tokens, 480 s, 0.50 USD), plus a gate that allows 2 model calls at a time and makes all workers wait after a rate limit. A new reporter multi command runs it.
  • R0 fixes carried in: fetch_page now checks the content type before downloading (PDFs are refused up front) and has a total time limit. 106 tests pass (29 new) and ruff is clean; tests use fake models and tools, no network.

How it works

flowchart LR
  subgraph inside["Inside one worker (plain Python loop)"]
    direction LR
    TH["think"] --> AC["act: search or fetch"]
    AC --> TH
    TH --> FIN["finalize: findings"]
  end
  FIN --> OK{"at least 1 finding
from fetched pages?"}
  OK -- "yes" --> DONE(["complete"])
  OK -- "no, attempt 1" --> RETRY["retry once with a failure note"]
  RETRY --> TH
  OK -- "no, attempt 2" --> INC(["incomplete"])

At most 3 workers run at once. Every model call goes through a gate with 2 slots, so a third worker can fetch a page while two others wait for the model. After an HTTP 429 the gate sets a shared cooldown (10 s, then 20 s, capped at 30 s) and every worker waits it out before its next call. Workers cite with small local numbers; merge assigns global numbers by section order, so the numbering does not depend on which worker finishes first. A section counts as complete when at least one finding survives, even if its loop stopped on max_steps or worker_time.

A shared cooldown stops 3 workers from hitting the same 429 in turn. Overshoot is bounded by the calls already in flight.

What broke, and what was fixed

The multi-agent system did not beat the baseline in these runs. It did what it was built for (parallel workers, retries, bounded budgets), but on the free tier the model limits decided the outcome more than the design did. One run produced a partly usable digest and one did not.
What brokeEvidenceStatus
Empty Groq replies, more than in R0. Steps with an empty-reply note: 12 of 34 calls (small LMs) and 22 of 30 (carbon capture). Unparseable-reply notes: 10 and 18. Not fixed. Only mitigated by the R0 retry at a higher temperature and the per-worker retry. A likely cause of the carbon-capture failure; not proven.
A Groq tokens-per-minute 429 killed a worker. Carbon-capture section s2 ended with provider_error (AllProvidersFailedError wrapping a 429 for openai/gpt-oss-120b), after the gate's one retry. Not fixed. The shared cooldown softens it but the 429 persisted past one retry. Not re-run.
The step budget cut sections short. Carbon capture: s4 and s5 stopped on budget_steps (shared run budget at 29 of 36 steps; the 80% stop point is 28.8) before any page was fetched. Tokens, seconds and cost were far below their limits. Retries spend steps too. Not fixed. The step limit is a starting default, not a tuned value. Whether to raise it is an open question for R3.
Retries did not recover sections. 3 retry attempts (s4 in small LMs; s1 and s3 in carbon capture), all ended incomplete. Their durations: 8.6 s, 9.6 s and 100.3 s. Working as designed (retry once, then incomplete), but not useful in these runs.
Carbon capture: no page read at all. 0 sources, 10 tool calls, all searches. The digest has no findings. Reported as is, no re-run (the run did not crash, so the one-time re-run allowance was not used).
The R0 PDF time sink. Longest tool call 7.88 s and 2.79 s; 0 calls over 20 s; 0 PDF errors. One fetch_page failure remained (an IEEE page with no readable text). Fixed: the content type is checked before the download and a total deadline applies.

Not measured: per-call start times (only worker start and end are traced), so slot contention is inferred from the rate-limit waits, not measured directly.

PR #2 (merged).

R2 · Critic and writer built, PR link added when opened

What was built

  • Deterministic citation checks (no model): they parse every citation form ([5], [5, 6], [5][6], [5-7]) and report invalid numbers, sources that are listed but never cited, and URLs that no fetch_page call of the run produced.
  • A critic that grades each section against a 4-point rubric (every claim sourced, the source supports the claim, no contradiction between sections, coverage of the plan) as pass, weak or fail. A section with no fetched page or no finding fails deterministically and never goes to the model.
  • One retry round: up to 3 weak or failed sections go back to their worker once, with the critic's issues as feedback. The retry replaces the original only if it is strictly better.
  • A writer that writes the body from the findings; the code builds the numbered Sources list and a Coverage notes section. Claims the critic marks unsupported are left out of the text and listed as unverified.
  • Every step has a fallback, and report text is sanitised (no raw provider errors or internal tokens). 140 tests pass (135 after the first build, 5 added by the fix) and ruff is clean, as checked by the main session; tests use fake models and tools, no network.

How it works

There is no loop in the graph: the retry branch can be traversed once, so the retry cap holds by construction (and a section already retried is refused again, which a test covers). The retry gate checks what a retry needs rather than the 70% line: no limit past 85%, at least 30 s left before 85% of the time limit, and about 3 run steps per retried section. Retry workers stop researching at 90%. The critic, re-grade and writer still stop at 100%. "Best attempt" is compared as (verdict rank, fetched pages, findings), and the final merge is redone from the chosen results so global source numbers follow section order.

DecisionRejectedWhy
A straight line with one retry branch.A critic-retry loop until sections pass.The retry cap holds by construction, not by a counter that could be wrong. Free-tier capacity is the bottleneck, so an open-ended loop is the wrong risk.
Keep the best attempt by (verdict rank, fetched pages, findings), replacing only if strictly better.Always take the retry.A retry that did worse must not overwrite a section. The order is deterministic and testable.
Research stops at 70% of any limit; the last 30% is reserved for critic, re-grade and writer.Spend the whole budget on research.Otherwise there is nothing left to grade or write with. The first evaluation shows the cost: the reserve was too tight on steps (see below).

What broke, and what was fixed

The retry has not yet been shown to improve a section. The mechanics work; the evidence that they help does not exist yet.
What brokeEvidenceStatus
First evaluation: the retry never ran. Research used 26 of 36 run steps (0.722, above the 0.70 stop line). Both runs recorded retry_skipped: 0 sections sent back, although 5 of 5 sections in each run were candidates. Fixed: run step limit 36 to 60, and a separate retry gate at 85% with its own worker stop fraction of 0.9. Verified in the second evaluation, where the gate opened once (1 of 2 runs).
First evaluation: raw provider error text leaked into a report. The small-language-model report contained a rate-limit error string with an organisation id and a billing URL, and three internal tokens in square brackets in section bodies. Fixed: plain-language reasons ("rate limited", "model output unusable", ...) and URL and token stripping. The leak check found zero hits in both second-evaluation reports. Caveat: the sanitiser was exercised by 1 report with "time limit reached / model output unusable" reasons and 1 with "rate limited" reasons.
Second evaluation: the retries did not help. 3 of 5 sections retried, 0 improved / 3 unchanged / 0 worse. All stayed at 0 pages and 0 findings. The retries failed on empty Groq replies, HTTP 403 pages and timeouts. Not fixed. The effect of a retry when fetches succeed is not measured.
Second evaluation: the carbon-capture run produced no report. All 5 sections ended on a provider rate-limit error for the Groq daily token limit (200,000; 198,673 to 198,899 used at the failed calls). The writer ran no model call (no_report: "No report could be written"). Not a pipeline result: it says nothing about the design. The "no findings" fallback did work. Not re-run. Why the second provider did not take over is not measured.
The unverified-claim filter looks too strict. In the small-language-model run the critic marked 4 claims unsupported and the writer left them out. At least 3 of the 4 are on the live source page (F32 weights, torch.float16 loading, 585 downloads last month). Whether they were inside the excerpt the critic saw is not measured. Not fixed. The false-positive rate cannot be quantified from n=4 claims on one page.
A claim overstates its source. The small-language-model report says TinyLlama "was pretrained on a 3 trillion-token corpus"; the page says the project "aims to pretrain" on 3 trillion tokens and that this chat model is fine-tuned from a 503B-token checkpoint. Not fixed. Claim-level support checks stay a gap.

Summary, honestly

The R2 mechanics work: the checks, the critic, the retry cap, the writer and the sanitised text behave as designed, and 11 of 11 citations in the small-language-model report are valid. What is not shown: that a retry improves a section, that the reports are good (the judge is R3), and that the range and multi citation forms work on real text. Both evaluations have n=1 per topic, and the second used changed code. Neither evaluation produced a report that covers its plan: at best 2 of 5 sections have text.
